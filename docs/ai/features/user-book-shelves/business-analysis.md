# Бизнес-анализ

## Фича

**Книжные полки пользователя (User Book Shelves)**

Feature slug: `user-book-shelves`

Соответствует Фазе 2 ROADMAP («Книжные полки (Shelves)», приоритет: высокий).

Полки — персональная библиотека пользователя: пользователь отмечает книги статусами «Хочу прочитать», «Читаю», «Прочитал», «Брошено» и добавляет в «Избранное». Это ключевая фича Goodreads-подобного продукта и фундамент всех персонализированных сценариев (рейтинги, рецензии, рекомендации, профили).

### Текущее состояние кодовой базы (источник истины)

По результатам исследования репозитория:

- Таблицы `shelves` и `shelf_items` уже созданы миграцией `backend/migrations/000001_initial.up.sql`:
  - `shelves`: `id UUID PK`, `user_id FK→users (ON DELETE CASCADE)`, `name VARCHAR(255) NOT NULL`, `type shelf_type ENUM('reading','read','want_to_read','abandoned','favorite','custom') DEFAULT 'custom'`, `created_at`, `updated_at`, **`UNIQUE(user_id, type)`**;
  - `shelf_items`: `shelf_id FK→shelves (ON DELETE CASCADE)`, `book_id FK→books (ON DELETE CASCADE)`, `added_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`, `PK(shelf_id, book_id)`;
  - индекс `idx_shelves_user_id` существует.
- Модуль `backend/internal/modules/shelves/` — директория `domain/` **пуста**. В ROADMAP заявлены «заготовки моделей», фактически их нет (расхождение документации с кодом — учтено в рисках, R-002).
- API, репозиторий, сервис и транспорт для shelves не реализованы. Роуты регистрируются в `backend/internal/transport/http/router.go` (публичные) и `backend/cmd/api/main.go` (защищённые через `middleware.Auth`).
- Auth middleware готов: `Auth` (обязательная), `OptionalAuth`, `RequireRole`; кладёт `user_id` (string) и `user` (*domain.User) в контекст Echo.
- Frontend: Next.js middleware уже защищает роут `/shelves` (вместе с `/profile`); в `@bookhaven/api-client` уже определён тип `Shelf`; страница книги `/books/[slug]` — серверный компонент без элементов управления полками; в Header нет ссылки на полки.
- Каталог фильтрует скрытые книги (`is_hidden = false`) — этот паттерн должен распространяться на содержимое полок.

### Ключевые продуктовые решения и их обоснование

**Решение 1. MVP = 5 стандартных полок; кастомные полки — отдельный инкремент.**

Анализ конфликта `UNIQUE(user_id, type)`:

- Ограничение гарантирует, что у пользователя не более одной полки каждого типа. Для стандартных типов (`want_to_read`, `reading`, `read`, `abandoned`, `favorite`) это **корректное и полезное** ограничение — оно энфорсит канонический набор полок на уровне БД.
- Для типа `custom` ограничение **блокирует более одной кастомной полки**, что противоречит продуктовому смыслу кастомных полок (у Goodreads их неограниченное количество).

Рассмотренные варианты:

| Вариант | Оценка |
|---|---|
| a) MVP: только стандартные полки, кастомные отложить | ✅ Рекомендуется. Не требует миграции, доставляет основную ценность, соответствует списку задач Фазы 2 в ROADMAP (эндпоинты и UI Фазы 2 не содержат управления кастомными полками) |
| b) MVP: стандартные + ровно одна кастомная | ❌ Не рекомендуется. Неестественный UX («почему только одна?»), ограничение придётся раскручивать назад |
| c) MVP: неограниченные кастомные полки через миграцию | ❌ Для текущего инкремента. Требует миграции (заменить `UNIQUE(user_id, type)` на partial unique index `WHERE type <> 'custom'`), CRUD полок, UI управления и **нерешённого продуктового вопроса об эксклюзивности кастомных полок** (в схеме нет колонки `is_exclusive`) — значительное расширение объёма |

Рекомендация для будущего инкремента кастомных полок: миграция с partial unique index (стандартные типы остаются уникальными per-user, `custom` — свободными). Конкретное решение — зона ответственности архитектора; здесь зафиксирована потребность.

**Решение 2. Ленивая материализация стандартных полок (get-or-create).**

Пользователь всегда видит канонический набор из 5 стандартных полок (включая пустые, со счётчиком 0) с момента первого обращения. Отсутствующие полки создаются автоматически при первом запросе списка полок или первом добавлении книги.

Обоснование (против альтернативы «создавать 5 полок при регистрации»):

- не требуется изменять процесс регистрации (нет межмодульной зависимости auth → shelves);
- работает для уже существующих пользователей без backfill-миграции;
- API всегда возвращает консистентный набор из 5 полк — упрощает контракт для frontend.

**Решение 3. Статусные полки взаимоисключающие; «Избранное» — независимое.**

- Полки `want_to_read`, `reading`, `read`, `abandoned` образуют группу «статус чтения» и **взаимоисключающие**: добавление книги на одну из них автоматически удаляет книгу с трёх остальных (атомарно, в одной транзакции). Это ключевая UX-логика Goodreads.
- Полка `favorite` — **независимый флаг**: книга может одновременно находиться на «Прочитал» и в «Избранном». Семантика «избранного» не является статусом чтения; исключение «избранного» из группы исключения предотвращает абсурдный UX (отметка любимой книги «в избранном» удаляла бы её из «Прочитал»).
- Отклонение от буквального прочтения «при добавлении на одну стандартную полку книга удаляется с других стандартных» зафиксировано как открытое подтверждение — см. OQ-002.

**Решение 4. Точка входа управления полками — страница книги.**

Кнопки «Хочу прочитать / Читаю / Прочитал» размещаются на детальной странице книги `/books/[slug]` (клиентский компонент поверх серверной страницы). Кнопки на карточках в каталоге `/books` отложены — требуется batch-получение статусов для N книг (см. OQ-004).

## Бизнес-цель

Полки — ядро петли удержания (retention loop) BookHaven:

```
каталог → «Хочу прочитать» → возврат на сайт → «Читаю» → «Прочитал» → рецензия/оценка (Фаза 3)
```

Без полок продукт — пассивный справочник. С полками — личная библиотека, ради которой пользователь возвращается.

Бизнес-цели:

1. **Активация**: дать новому пользователю первое персональное действие в течение первой сессии (добавить книгу на полку).
2. **Удержание**: создать причину для повторных визитов (список «Хочу прочитать», статус «Читаю»).
3. **Фундамент монетизации и рекомендаций**: данные о статусах чтения — основа будущих рекомендаций, подборок и аналитики поведения.
4. **Конкурентный паритет**: для рынка РФ/СНГ воспроизвести базовый уровень Goodreads / StoryGraph / ЛитРес в локализованном виде.

Целевые метрики (для последующего измерения, не входят в объём реализации):

- доля зарегистрированных пользователей, добавивших ≥ 1 книги на полку в первой сессии;
- доля активных пользователей с ≥ 1 книгой в статусах «Читаю»/«Прочитал» за 30 дней;
- retention D7/D30 пользователей с полками против пользователей без полок.

## Проблема пользователя

1. Пользователь находит книгу в каталоге, но **не может сохранить её «на потом»** — закрыл вкладку и потерял.
2. Нет способа **вести историю прочитанного** и список текущего чтения.
3. Нет способа отметить **брошенные книги**, чтобы не возвращаться к неинтересным.
4. Нет «избранного» для быстрого доступа к любимым книгам.
5. Конкуренты дают эти возможности из коробки; у пользователя нет локализованной альтернативы для рынка РФ/СНГ.

## Целевые пользователи

| Сегмент | Роль в системе | Потребность |
|---|---|---|
| Читатель (основной сегмент, `profile_type=reader`) | любая роль: `user`, `contributor`, `moderator`, `admin` | вести личную библиотеку: «хочу прочитать», «читаю», «прочитал», «избранное» |
| Библиотекарь / книготорговец (`librarian`, `bookseller`) | те же | быстрые списки для работы (в будущем — кастомные полки и списки, Фаза 5) |
| Анонимный посетитель | не аутентифицирован | увидеть, что персонализация существует, и зарегистрироваться |

Для полок роли функционально равны: право на полки даёт аутентификация, а не роль. Модерация чужих полок не предусмотрена (см. «Что не входит в фичу»).

## Пользовательские истории

- **US-001**. Как читатель, я хочу отметить книгу как «Хочу прочитать», чтобы не забыть о ней и вернуться к ней позже.
- **US-002**. Как читатель, я хочу отметить книгу как «Читаю», чтобы видеть свой актуальный список текущего чтения.
- **US-003**. Как читатель, я хочу отметить книгу как «Прочитал», чтобы вести историю прочитанного.
- **US-004**. Как читатель, я хочу отметить книгу как «Брошено», чтобы зафиксировать, что к ней возвращаться не планирую.
- **US-005**. Как читатель, я хочу добавить книгу в «Избранное», чтобы быстро находить любимые книги независимо от статуса чтения.
- **US-006**. Как читатель, я хочу видеть все свои полки с количеством книг на каждой, чтобы ориентироваться в своей библиотеке.
- **US-007**. Как читатель, я хочу просматривать содержимое полки постранично, чтобы работать даже с очень большими полками.
- **US-008**. Как читатель, я хочу убрать книгу с полки, если передумал или ошибся.
- **US-009**. Как анонимный посетитель, я хочу после клика на кнопку полки попасть на страницу входа и после входа вернуться к той же книге, чтобы быстро сохранить книгу.

## Пользовательские сценарии

### SCN-001. Добавление книги в «Хочу прочитать» (основной happy path)

- **Актёр**: аутентифицированный пользователь.
- **Предусловия**: пользователь на странице `/books/[slug]`; книга не находится ни на одной его полке.
- **Шаги**:
  1. Пользователь нажимает кнопку «Хочу прочитать».
  2. Полка `want_to_read` материализуется (если ещё не существует), книга добавляется на неё.
  3. Кнопка «Хочу прочитать» переходит в активное (подсвеченное) состояние без перезагрузки страницы.
- **Результат**: книга присутствует на полке «Хочу прочитать»; счётчик полки увеличился на 1.

### SCN-002. Перемещение книги по статусам

- **Актёр**: аутентифицированный пользователь.
- **Предусловия**: книга находится на полке «Хочу прочитать».
- **Шаги**:
  1. Пользователь начинает читать книгу и нажимает «Читаю».
  2. Система атомарно удаляет книгу с «Хочу прочитать» и добавляет на «Читаю».
  3. Пользователь завершает книгу и нажимает «Прочитал».
  4. Система атомарно перемещает книгу с «Читаю» на «Прочитал».
- **Результат**: в каждый момент книга находится ровно на одной статусной полке; на странице книги подсвечена актуальная.

### SCN-003. Брошенная книга

- **Актёр**: аутентифицированный пользователь.
- **Предусловия**: книга на полке «Читаю».
- **Шаги**: пользователь открывает вторичное меню статусов на странице книги и выбирает «Брошено».
- **Результат**: книга перемещена с «Читаю» на «Брошено».

### SCN-004. Избранное поверх статуса

- **Актёр**: аутентифицированный пользователь.
- **Предусловия**: книга на полке «Прочитал».
- **Шаги**: пользователь нажимает «Избранное» (toggle).
- **Результат**: книга находится одновременно на «Прочитал» и в «Избранном»; статус чтения не изменился.

### SCN-005. Удаление книги с полки

- **Актёр**: аутентифицированный пользователь.
- **Предусловия**: книга на полке «Читаю» и в «Избранном».
- **Шаги**: пользователь на странице книги (или на странице полки) выполняняет явное действие «Убрать с полки» для статусной полки.
- **Результат**: книга удалена со статусной полки; остаётся в «Избранном».

### SCN-006. Просмотр своих полок

- **Актёр**: аутентифицированный пользователь.
- **Шаги**:
  1. Пользователь открывает `/shelves` (или переходит по ссылке «Мои полки» в Header).
  2. Видит 5 стандартных полок с названиями и счётчиками книг (у нового пользователя — все с 0).
  3. Выбирает полку — видит сетку карточек книг, добавленных позже — первыми; при > 20 книгах — постраничная навигация.
- **Результат**: пользователь может просмотреть любую свою полку.

### SCN-007. Анонимный посетитель на странице книги

- **Актёр**: анонимный посетитель.
- **Шаги**:
  1. Посетитель открывает `/books/[slug]` — элементы управления полками видимы.
  2. Нажимает «Хочу прочитать».
  3. Система перенаправляет на `/login?redirect=/books/[slug]`.
  4. Посетитель входит — возвращается на страницу той же книги.
- **Результат**: конверсионный путь «увидел → залогинился → сохранил» работает без потери контекста.

### SCN-008. Попытка изменить чужую полку (IDOR)

- **Актёр**: аутентифицированный пользователь A.
- **Предусловия**: существует полка пользователя B.
- **Шаги**: A отправляет API-запрос на добавление/удаление книги с полкой_id полки пользователя B.
- **Результат**: запрос отклонён (403 или 404 — решение архитектора, рекомендация 404), изменения не применены, A не получает подтверждения существования чужой полки.

### SCN-009. Истёкший access-токен в момент действия

- **Актёр**: пользователь с просроченным access-токеном (cookie ещё присутствует).
- **Шаги**: пользователь нажимает кнопку полки; API отвечает 401.
- **Результат**: frontend корректно обрабатывает 401 (попытка refresh или редирект на `/login?redirect=...`); кнопка возвращается в исходное состояние; книга не добавлена «молча».

### SCN-010. Книга скрыта модератором после добавления на полку

- **Актёр**: пользователь с книгой X на полке «Читаю»; администратор скрывает книгу X (`is_hidden = true`).
- **Результат**: книга X не отображается в содержимом полки и не учитывается в счётчике; запись в `shelf_items` сохраняется (книга вернётся при снятии скрытия).

## Функциональные требования

> Формулировки описывают возможности. Конкретные формы эндпоинтов — зона ответственности архитектора; базовая линия — ROADMAP Фаза 2: `POST /api/v1/shelves/:id/books`, `DELETE /api/v1/shelves/:id/books/:book_id`, `GET /api/v1/users/:id/shelves`.

- **FR-001**. Система поддерживает канонический набор из 5 стандартных полк каждого пользователя с фиксированными типами и названиями: `want_to_read` («Хочу прочитать»), `reading` («Читаю»), `read` («Прочитал»), `abandoned` («Брошено»), `favorite` («Избранное»). Стандартные полки нельзя создавать, переименовывать или удалять по отдельности.
- **FR-002**. При первом обращении пользователя к своим полкам (запрос списка полок или добавление книги) отсутствующие стандартные полки создаются автоматически (ленивая материализация). Запрос списка полк пользователя всегда возвращает все 5 стандартных полк, включая пустые.
- **FR-003**. Аутентифицированный пользователь может добавить книгу на стандартную полку непосредственно со страницы книги `/books/[slug]`.
- **FR-004**. Статусные полки (`want_to_read`, `reading`, `read`, `abandoned`) взаимоисключающие: при добавлении книги на одну из них книга автоматически удаляется с трёх остальных. Операция выполняется атомарно: в любой момент книга находится не более чем на одной статусной полке.
- **FR-005**. Полка `favorite` независима от статусных полк: добавление/удаление книги в «Избранное» не изменяет статусную полку, и наоборот.
- **FR-006**. Повторное добавление книги на полку, где она уже находится, — идемпотентная операция: успешный ответ (2xx), без дубликата, без изменения `added_at`.
- **FR-007**. Аутентифицированный пользователь может удалить книгу со своей полки: со страницы книги (явное действие «Убрать с полки» для статусной полки; повторное нажатие «Избранное» — снятие) и со страницы полки.
- **FR-008**. Список полк пользователя возвращает для каждой полки: `id`, `type`, `name`, `books_count` (количество книг). Для стандартных полк `name` детерминированно определяется типом.
- **FR-009**. Содержимое полки доступно постранично: параметры `page` (≥ 1) и `limit` (1–100, по умолчанию 20); сортировка по `added_at` по убыванию. Элемент списка содержит данные книги (как в карточке каталога: `id`, `title`, `slug`, `cover_url`, `authors`, `rating` и т. д.) и `added_at`. Скрытые книги (`is_hidden = true`) в список не включаются.
- **FR-010**. Для аутентифицированного пользователя система предоставляет способ определить, на каких его полках находится книга, — для отображения активного состояния элементов управления на странице книги (точный механизм — эндпоинт или расширение ответа детальной книги — определяет архитектор).
- **FR-011**. Для неаутентифицированного пользователя элементы управления полками на странице книги видимы; при попытке любого действия выполняется редирект на `/login?redirect=<путь текущей страницы>`.
- **FR-012**. Страница `/shelves` (защищена middleware) отображает 5 стандартных полк с названиями и счётчиками; выбор полки показывает её содержимое (сетка карточек книг, пагинация при > 20 книгах).
- **FR-013**. Header сайта содержит ссылку «Мои полки» на `/shelves` для аутентифицированных пользователей (скрыта для анонимных).
- **FR-014**. `books_count` полки соответствует количеству видимых (не `is_hidden`) книг на полке.

## Нефункциональные требования

- **NFR-001**. Защита от IDOR: все операции записи с полкой требуют, чтобы полка принадлежала аутентифицированному пользователю; обращение к чужой полке отклоняется без раскрытия факта её существования (рекомендация — 404).
- **NFR-002**. Перемещение книги между статусными полками выполняется в одной транзакции БД (все удаления и вставки — «всё или ничего»).
- **NFR-003**. Производительность списков: содержимое полки никогда не возвращается без пагинации (не более 100 книг за запрос); список полк со счётчиками получается без N+1-запросов.
- **NFR-004**. Идемпотентность операций добавления гарантируется на уровне БД (PK `shelf_items`) и API (повторный запрос не создаёт дублей и не возвращает ошибку).
- **NFR-005**. Локализация: подписи полк в UI — на русском языке («Хочу прочитать», «Читаю», «Прочитал», «Брошено», «Избранное»); API оперирует типами enum, UI отображает русские названия.
- **NFR-006**. Доступность: элементы управления полками доступны с клавиатуры, имеют текстовые подписи (не только иконки/цвет).
- **NFR-007**. Отказоустойчивость UI: при ошибке API состояние элементов управления полками откатывается к фактическому; пользователь видит ненавязчивое сообщение об ошибке; «молчаливое» добавление невозможно.
- **NFR-008**. Соответствие существующим паттернам проекта: модуль `shelves` строится по образцу `catalog` (domain → repository → service → transport/http с DTO); frontend использует `@bookhaven/api-client` (расширяется методами shelves) и существующие UI-компоненты; изменения схемы БД выполняются только через миграции (для MVP стандартных полк миграция не требуется).

## UX-требования

### Страница книги `/books/[slug]`

- Блок управления полками размещается заметно (рядом с обложкой/заголовком), не ниже первого экрана.
- Три первичные кнопки: **«Хочу прочитать»**, **«Читаю»**, **«Прочитал»**.
- Вторичное меню (например, «⋯» или выпадающий список): **«Брошено»** и переключатель **«Избранное»** (иконка закладки/сердца с состоянием).
- Активная статусная кнопка визуально выделена (заливка/цвет); повторный клик по активной статусной кнопке не выполняет действия (кнопка неактивна) — снятие статуса только через явное «Убрать с полки» (см. OQ-005).
- «Избранное» — toggle: нажатие добавляет, повторное — убирает.
- Действие применяется без полной перезагрузки страницы (клиентский компонент); на время запроса кнопка в состоянии загрузки (защита от двойного клика).
- Для анонимного пользователя блок видим; клик по любому действию → `/login?redirect=<текущий путь>`.

### Страница `/shelves`

- Вкладки или вертикальный список полк: русское название + счётчик («Прочитал · 42»).
- Содержимое полки — сетка карточек книг, единообразная с каталогом `/books`; клик по карточке → страница книги.
- Пагинация в стиле каталога («Назад / Страница N из M / Вперед»).
- Пустое состояние полки: сообщение «Полка пуста» + ссылка на каталог («Найти книги в каталоге»).
- На карточке книги на полке — действие удаления книги из этой полки (явная иконка ×, без диалога подтверждения: операция низкорисковая и обратимая).

### Header

- Ссылка «Мои полки» рядом с «Каталог» для аутентифицированных пользователей.

### Обработка ошибок в UI

- Ошибки API (401/403/404/400/5xx/сеть) отображаются ненавязчивым сообщением (toast или inline), состояние кнопок откатывается.
- 401 инициирует сценарий SCN-009 (refresh/редирект на логин с возвратом).

## Требования к валидации

Входные данные API:

- `book_id` — обязательный, валидный UUID, книга существует и не скрыта (`is_hidden = false`).
- `shelf_id` (для эндпоинтов, идентифицирующих полку) — обязательный, валидный UUID, полка существует и принадлежит текущему пользователю.
- `type` (если API оперирует типом полки) — одно из значений `shelf_type`; в MVP принимаются только 5 стандартных типов; `custom` отклоняется с 400 до реализации кастомных полок.
- Пагинация: `page` ≥ 1 (по умолчанию 1), `limit` 1–100 (по умолчанию 20); некорректные значения — 400 или приведение к умолчаниям (решение архитектора, поведение задокументировано).
- Тело запроса — корректный JSON; нарушение схемы — 400.

Frontend:

- Формы не требуются (действия — кнопки без свободного ввода); валидация сводится к обработке ответов API.
- Защита от двойной отправки: кнопка блокируется на время выполнения запроса.

## Граничные случаи

- **Пустой аккаунт**: новый пользователь открывает `/shelves` — видит 5 полк со счётчиками 0 (материализация по FR-002).
- **Книга уже на полке**: повторное добавление — идемпотентно (FR-006), `added_at` не меняется.
- **Книга на «Избранном» + статусной полке одновременно**: валидное состояние (FR-005).
- **Перемещение на ту же статусную полку**: no-op, успешный ответ, без изменений.
- **Книга скрыта после добавления**: не отображается в полке и в счётчике; запись сохраняется (SCN-010, FR-014).
- **Книга удалена из каталога**: `ON DELETE CASCADE` удаляет записи из `shelf_items` автоматически.
- **Пользователь удалён**: `ON DELETE CASCADE` удаляет его полки автоматически.
- **Большая полка** (1000+ книг): пагинация, не более 100 книг за запрос (FR-009, NFR-003).
- **Ровно 20 / 21 книга на полке**: 20 → одна страница; 21 → две страницы (2-я с одной книгой).
- **`limit` на границе**: `limit=100` — валиден; `limit=101` — приводится к 100 или 400 (по решению архитектора).
- **Истёкший access-токен при открытом `/shelves`**: middleware пропускает (проверяет только наличие cookie — известное ограничение, R-005); API возвращает 401; UI обрабатывает (SCN-009).
- **Книга без обложки на полке**: карточка с заглушкой «Нет обложки» (как в каталоге).

## Критерии приемки

> Все критерии проверяемы через API (curl/HTTP-клиент с cookie `access_token`) или через UI. Формы эндпоинтов соответствуют архитектурному документу; базовая линия — ROADMAP Фаза 2.

- **AC-001**. Аутентифицированный пользователь добавляет книгу на полку «Хочу прочитать» → ответ 2xx; в списке полк `want_to_read` имеет `books_count = 1`; книга присутствует в содержимом полки.
- **AC-002**. Книга находится на `want_to_read`; пользователь добавляет её на `reading` → ответ 2xx; книга отсутствует в `want_to_read` и присутствует в `reading`.
- **AC-003**. Книга находится на `reading`; через UI страницы книги пользователь нажимает «Прочитал» → книга перемещена на `read` (проверяется API или UI).
- **AC-004**. Книга находится на `read`; пользователь добавляет её в `favorite` → книга присутствует **и** в `read`, **и** в `favorite` одновременно.
- **AC-005**. Книга уже на полке; повторное добавление на ту же полку → ответ 2xx, дубль в содержимом отсутствует, `added_at` не изменился, `books_count` не увеличился.
- **AC-006**. Пользователь удаляет книгу со статусной полки (API) → ответ 2xx; книга отсутствует в содержимом полки; `books_count` уменьшился на 1.
- **AC-007**. Книга на `read` и в `favorite`; удаление со статусной полки → книга удалена с `read`, но осталась в `favorite`.
- **AC-008**. Новый пользователь запрашивает список своих полк → 5 полк со стандартными типами, у каждой `books_count = 0`.
- **AC-009**. Неаутентифицированный запрос на добавление книги на полку → 401; книга не добавлена.
- **AC-010**. Запрос с `shelf_id` полки другого пользователя → 403 или 404; изменения не применены.
- **AC-011**. Запрос с `book_id`, не являющимся UUID → 400.
- **AC-012**. Запрос с `book_id` несуществующей или скрытой книги → 404.
- **AC-013**. На полке 25 книг; запрос содержимого с `limit=20` → страница 1 содержит 20 книг, страница 2 — 5, `total = 25`.
- **AC-014**. Книга на полке помечена `is_hidden = true` → она отсутствует в содержимом полки и не учитывается в `books_count`.
- **AC-015**. Аутентифицированный пользователь открывает `/books/[slug]` → видны кнопки «Хочу прочитать», «Читаю», «Прочитал» и доступ к «Брошено»/«Избранному»; если книга на его полке — соответствующая кнопка в активном состоянии.
- **AC-016**. Анонимный пользователь на `/books/[slug]` нажимает «Хочу прочитать» → редирект на `/login?redirect=/books/<slug>`; после входа — возврат на страницу книги.
- **AC-017**. Анонимный запрос `/shelves` → редирект на `/login`; аутентифицированный → страница показывает 5 полк с названиями и счётчиками.
- **AC-018**. Header аутентифицированного пользователя содержит ссылку «Мои полки», ведущую на `/shelves`; у анонимного — нет.
- **AC-019**. Добавление книги на полку со страницы книги происходит без полной перезагрузки страницы (кнопка меняет состояние на активное).
- **AC-020**. Со страницы `/shelves` пользователь может удалить книгу из открытой полки → книга исчезает из списка, счётчик уменьшается.
- **AC-021**. В содержимом полки книги, добавленные позже, отображаются первыми (сортировка `added_at DESC`).
- **AC-022**. Удаление книги из «Избранного» (повторное нажатие toggle) → книга удалена из `favorite`, статусная полка не изменилась.

## Границы MVP

### In scope (MVP данной фичи)

- 5 стандартных полк с ленивой материализацией (FR-001, FR-002).
- Добавление/удаление книг, взаимоисключаемость статусных полк, независимость «Избранного» (FR-003–FR-007).
- API: список полк со счётчиками; содержимое полки с пагинацией; добавление/удаление книги (FR-008, FR-009).
- Статус книги пользователя для страницы книги (FR-010).
- UI: блок управления полками на `/books/[slug]`; страница `/shelves`; ссылка в Header (FR-011–FR-013).
- Обработка ошибок и граничных случаев по разделам «Сценарии ошибок» и «Граничные случаи».
- Расширение `@bookhaven/api-client` методами shelves (тип `Shelf` уже существует).

### Out of scope (не входит в MVP)

- Кастомные полки: создание, переименование, удаление, эксклюзивность (Решение 1; отдельный инкремент с миграцией).
- Публичный просмотр полк других пользователей в UI (страницы `/users/[id]/shelves`) — Фаза 6 (профили); см. OQ-003.
- Кнопки полк на карточках книг в каталоге `/books` — см. OQ-004.
- Кастомная сортировка и ручной порядок книг на полке (drag-n-drop).
- Массовые операции (выделить несколько книг, удалить пачкой, переместить пачкой).
- Экспорт/импорт полк (CSV и т. п.).
- Приватность полк (настройки видимости) — в схеме нет соответствующего поля.
- Статистика чтения (цели, страницы, прогресс чтения книги).
- Уведомления и напоминания («вы читаете уже N дней»).
- Интеграция статусов полк с рейтингами/рецензиями (Фаза 3).
- Модерация и административное управление полками пользователей.
- Изменения схемы БД (для MVP стандартных полк миграция не требуется).

## Открытые вопросы и риски

### Открытые вопросы

- **OQ-001. Кастомные полки: включать ли в текущий инкремент?** Рекомендация — нет (Решение 1): MVP стандартных полк не требует миграции и доставляет основную ценность; кастомные полки — отдельный инкремент с миграцией (partial unique index) и продуктовым решением об эксклюзивности кастомных полок. **Статус: не блокирует MVP стандартных полк; должен быть решён до планирования инкремента кастомных полок.**
- **OQ-002. Независимость «Избранного».** Задание формулирует исключительность для «стандартных полок» без различения; данный анализ рекомендует независимое «Избранное» (Решение 3) из семантики статуса чтения. **Статус: не блокирующий; требуется подтверждение продуктовой стороной до начала разработки (реализация тривиально меняется в любую сторону).**
- **OQ-003. Публичная видимость полк.** Схема не содержит настроек приватности; модель Goodreads — полки публичны. ROADMAP содержит `GET /api/v1/users/:id/shelves`. Рекомендация: в MVP реализовать только собственные полки; публичный просмотр — вместе с профилями (Фаза 6), где и решится вопрос приватности. **Статус: решено** (см. `docs/features/public-shelf-visibility.md`) — полки отображаются на публичном профиле безусловно, без настройки приватности (как и сам профиль, и списки/отзывы); флаг приватности для полок не добавлялся.
- **OQ-004. Кнопки полк на карточках в каталоге.** ROADMAP упоминает карточку книги, задание — только страницу книги. Для карточек нужен batch-статус для N книг. Рекомендация: отложить. **Статус: не блокирующий; зафиксировано отклонение от ROADMAP.**
- **OQ-005. Поведение клика по уже активной статусной кнопке.** Рекомендация: кнопка неактивна (no-op); снятие статуса — только явным «Убрать с полки». Альтернатива — toggle (клик снимает статус). **Статус: не блокирующий; решение по умолчанию — неактивна.**
- **OQ-006. Форма API для добавления книги на полку.** ROADMAP предлагает shelf-id-ориентированные эндпоинты (`POST /shelves/:id/books`); статус-ориентированная альтернатива (`POST /books/:id/shelf-status`) упрощает логику перемещения. **Статус: не блокирующий; относится к архитектурному анализу, зафиксировано здесь как вход.**

### Риски

- **R-001 (средний)**. Конфликт `UNIQUE(user_id, type)` с кастомными полками: если продукт решит включить кастомные полки без миграции — реализация невозможна; с миграцией — потребуется изменение约束. Смягчение: Решение 1 (кастомные полки вне MVP) + задокументированная потребность в миграции.
- **R-002 (низкий)**. ROADMAP заявляет заготовки domain-моделей shelves, но директория пуста — трудозатраты выше, чем следует из документации. Смягчение: оценка по фактическому состоянию (модуль с нуля по образцу catalog).
- **R-003 (низкий)**. Производительность счётчиков: `COUNT` на каждый запрос списка полк. Для MVP приемлемо; мониторить при росте; оптимизация (денормализованный счётчик) — при необходимости.
- **R-004 (средний)**. Гонки при параллельных перемещениях книги между статусными полками. Смягчение: транзакционность (NFR-002) + идемпотентность (NFR-004); покрыть AC-005 и E-09/E-10 при QA.
- **R-005 (низкий, известный)**. Next.js middleware проверяет только наличие cookie `access_token`, не валидность — `/shelves` может открыться с просроченным токеном. Смягчение: корректная обработка 401 в UI (SCN-009); полная валидация в middleware — существующий пункт долга ROADMAP (Фаза 1).
- **R-006 (низкий, dev-only)**. Известная проблема WSL2 с hot-reload Go-файлов — после правок backend требуется `docker compose restart backend`.

## Зависимости

**Готово (не блокирует):**

- Auth: регистрация/логин, JWT в http-only cookies, `middleware.Auth`/`OptionalAuth` с `user_id`/`user` в контексте — используется как есть.
- Каталог: книги, фильтрация `is_hidden` — паттерн переиспользуется для содержимого полок.
- Frontend-аутентификация: middleware (уже защищает `/shelves`), Zustand auth store, Header.
- Схема БД: таблицы `shelves`/`shelf_items` существуют; для MVP миграция не требуется.
- `@bookhaven/api-client`: тип `Shelf` уже определён.

**Зависимости внутри фичи:**

- UI страницы книги зависит от FR-010 (статус книги пользователя) — реализуются вместе.
- Страница `/shelves` зависит от API списка полк и содержимого полки.

**Внешние зависимости (последующие фазы, не входящие):**

- Фаза 3 (рейтинги/рецензии) может опираться на статусы полк (например, подсказка «вы прочитали книгу — оцените её»).
- Фаза 6 (профили) — публичное отображение полк (OQ-003).

## Что не входит в фичу

Явно исключено из текущего инкремента (см. «Границы MVP → Out of scope»):

1. Кастомные полки (любая форма) — отдельный инкремент с миграцией БД.
2. Публичные страницы полк других пользователей.
3. Кнопки полк на карточках каталога `/books`.
4. Кастомная сортировка/порядок книг, drag-n-drop.
5. Массовые операции над книгами полки.
6. Экспорт/импорт полк.
7. Настройки приватности полк.
8. Статистика и цели чтения, прогресс по страницам.
9. Уведомления/напоминания.
10. Интеграция с рейтингами и рецензиями (Фаза 3).
11. Административная модерация полк.
12. Изменения схемы БД (в т. ч. миграция под кастомные полки).
