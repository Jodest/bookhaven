# Бизнес-анализ

## Фича

**Наполнение каталога данными книг (Catalog Data Import)**

Feature slug: `catalog-data-import`

Не входит явным пунктом в ROADMAP, но является предпосылкой для полноценного запуска: без объёма каталога (десятки/сотни/тысячи книг) все реализованные фичи (полки, рейтинги, поиск и фильтры, списки) работают на демонстрационных данных.

### Текущее состояние кодовой базы (источник истины)

По результатам исследования репозитория:

- **Модель данных.** `books` (`backend/migrations/000001_initial.up.sql`): `id UUID PK`, `title`, `slug UNIQUE NOT NULL`, `description`, `cover_url`, `isbn VARCHAR(20)` — **без уникального ограничения**, `published_year`, `page_count`, `language DEFAULT 'ru'`, `rating`/`ratings_count`/`reviews_count` (агрегаты, вычисляются приложением), `is_hidden`. Связи `book_authors`/`book_genres` — many-to-many через отдельные таблицы. Единственный естественный ключ дедупликации на уровне БД — `slug`; ISBN не уникален и не обязателен.
- **Способ №1 (существует): ручной ввод через админку.** `docs/features/admin.md` (статус: implemented) описывает `POST/PATCH /api/v1/admin/books` — создание/редактирование **одной книги за раз** через форму `apps/admin/src/features/manage-book/ui/book-form.tsx`. Сервис `backend/internal/modules/admin/service/service.go` уже содержит переиспользуемую логику: генерацию slug из названия (`slugify`), проверку его URL-безопасности и уникальности (`BookSlugExists`), валидацию ISBN-10/13 (`isValidISBN`), транзакционную замену связей автор/жанр. Авторы и жанры сопоставляются по существующим ID (не по имени) — форма ожидает, что автор/жанр уже создан.
- **Способ №2 (существует, для разработки): хардкод-скрипт `cmd/seed`.** `backend/cmd/seed/main.go` — Go-программа с ~19 книгами и 11 авторами, захардкоженными в исходном коде. Использует `db.FirstOrCreate` по `slug`/email, что делает запуск идемпотентным. Явно помечена как dev/demo-инструмент (создаёт тестовый аккаунт с известным паролем), запускается напрямую в БД в обход HTTP-API и авторизации. Технический долг `Makefile seed` в ROADMAP указывает, что даже этот путь не полностью формализован.
- **Данные каталога сейчас** — исключительно классика (Толстой, Достоевский, Оруэлл и т. д.), обложки — прямые ссылки на `covers.openlibrary.org`. Собственного хранилища изображений или пайплайна загрузки обложек нет.
- **Нет** ни одного из следующих механизмов: массовый импорт (CSV/JSON/Excel), интеграция с внешним книжным API (Google Books, Open Library, ЛитРес и т. п.), очередь/джоба фоновой обработки, черновик/ревью для вновь добавленных записей отдельно от `is_hidden`.
- **Инфраструктура фоновых задач отсутствует** — весь backend (`backend/cmd/api`) — синхронный HTTP-сервис на Echo; нет воркеров, очередей или cron в составе приложения (см. `docker-compose.yml`).

## Ключевые продуктовые решения и их обоснование

### Решение 1. Какой источник данных использовать для наполнения каталога?

**Обновлено по итогам обсуждения с продуктом.** У проекта нет готового файла с данными книг, и его подготовка — отдельная организационная работа, которую никто не выполняет. Поэтому направление сменилось: наполнение каталога строится **на программном импорте из открытых легальных внешних источников**, а не на ожидании курируемого файла. Подробный сравнительный анализ источников — в разделе «Источники данных: сравнительный анализ» ниже; здесь фиксируется только направление решения.

| Вариант источника | Оценка |
|---|---|
| a) Курируемый файл (CSV/JSON) от человека | ❌ Отклонено как основной путь — файла нет и не предвидится в обозримом времени. Остаётся технически поддержанным резервным путём (способ B ниже) на случай, если файл всё же появится (например, выгрузка от будущего издательского партнёра) |
| b) Программный импорт из открытых внешних источников (Wikidata, Open Library) | ✅ Рекомендуется как основной путь. Не требует ручной подготовки данных; масштабируется на весь объём, который покрывают источники; легально чисто при использовании источников с явной открытой лицензией (CC0) |
| c) Коммерческие/партнёрские источники (ЛитРес API, книготорговые агрегаторы) | ⚠️ Дают лучшее покрытие рынка РФ, но требуют заключения партнёрского соглашения — это не «открытые данные» в смысле вопроса, а отдельный бизнес-процесс вне объёма этого анализа. Зафиксировано как возможное направление роста после MVP |
| d) Автоматический скрапинг сторонних книжных сайтов (розничные магазины, фан-базы вроде fantlab.ru) | ❌ Не рекомендуется. Юридические риски (нарушение ToS, авторские права на описания/обложки), хрупкость (изменение вёрстки источника ломает импорт) |

**Рекомендация**: строить импорт на Wikidata (структурированные факты) с обогащением из Open Library (обложки, описания, дополнительные издания) — оба источника имеют явную открытую лицензию и не требуют соглашений. Google Books и партнёрские API рынка РФ рассмотрены отдельно и **исключены** из MVP по конкретным причинам (лицензия/договор) — см. ниже.

### Источники данных: сравнительный анализ (в т. ч. русский сегмент)

Ниже — источники, реально рассмотренные для наполнения каталога, с оценкой лицензии, покрытия и практической пригодности. Оценка по состоянию на момент анализа (данные о лицензиях/ToS проверены веб-поиском).

| Источник | Лицензия / условия | Покрытие RU-сегмента | Способ доступа | Вердикт |
|---|---|---|---|---|
| **Wikidata** (query.wikidata.org) | Все данные — **CC0** («no rights reserved», публичное достояние). Без ограничений на переиспользование | Хорошее для **известной/канонической** литературы: русская классика, авторы-нобелевские лауреаты, произведения со статьёй в ru.wikipedia — как правило, есть `ru`-подпись (label), автор, дата публикации, жанр (`instance of`/`genre`). Слабое для современной жанровой прозы, малотиражных изданий, самиздата — таких объектов в Wikidata обычно просто нет | SPARQL-запросы через публичный эндпоинт для точечных/умеренных выборок; **еженедельные полные дампы** для действительно объёмных выгрузок (сам проект просит не тянуть большие объёмы через живой SPARQL-эндпоинт) | ✅ **Основной источник структурированных фактов** для MVP |
| **Open Library** (openlibrary.org) | Метаданные — CC0 (условие для контрибьюторов); дампы и API документированы и предназначены для внешнего использования | Хорошее для переводных изданий классики на разных языках (в т. ч. многие русские классики представлены изданиями на английском); заметно слабее для метаданных именно русскоязычных оригинальных изданий и русских ISBN | REST API (Books API, Search API) и **Covers API** (`covers.openlibrary.org` — уже используется в seed-данных проекта) для единичных/точечных запросов; **ежемесячные дампы** (JSON: editions/works/authors) для массовой выгрузки. Проект прямо просит не использовать live-API для bulk-скачивания — для этого дампы | ✅ **Источник обложек и обогащения** (описание, page count, альтернативные издания) для MVP |
| **Google Books API** | ToS явно запрещает создавать/сохранять базу данных из результатов API, кэшировать дольше срока из cache-заголовков и распространять/публично показывать контент без отдельного разрешения правообладателя | Широкое покрытие, включая много русскоязычных изданий (Google активно сканировал/индексировал) | REST API | ❌ **Не подходит как источник для постоянного хранения** в нашей БД — противоречит цели фичи (наполнить каталог = сохранить данные надолго). Использование допустимо только как эфемерная подсказка при живом поиске без сохранения результата, что не решает задачу массового наполнения — **исключён из MVP** |
| **ЛитРес** (партнёрский REST/XML API) | Доступ только по индивидуальному ключу после заключения договора; условия использования каталога определяются договором, не публичной открытой лицензией | Лучшее покрытие именно современного русскоязычного книжного рынка среди всех рассмотренных вариантов | Партнёрский API (поиск/каталог/авторы/жанры), нужен подписанный договор | ⚠️ Не «открытые данные» в смысле вопроса — бизнес-партнёрство, а не самостоятельно доступный источник. Зафиксировано как **направление роста после MVP**, не как часть текущего анализа |
| **РГБ / РНБ / НЭБ** (национальные библиотеки РФ) | Библиографические записи как факты обычно не являются объектом авторского права; формальных ограничений на базовый поиск не обнаружено | Потенциально лучшее покрытие именно российских изданий (это национальные каталоги) | РГБ принимает запросы по протоколу **Z39.50** (RUSMARC); современного REST/JSON API или готовых bulk-дампов в открытом доступе в ходе анализа не обнаружено | ⚠️ Теоретически самый авторитетный источник для российских изданий, но: нужен Z39.50-клиент (устаревший протокол, не JSON), нет документированных лимитов/SLA для внешних разработчиков, инженерные затраты высокие и заранее не оцениваемые. **Не входит в MVP**; кандидат на отдельный технический спайк, если понадобится глубина именно по российским изданиям |
| **Российская книжная палата** (национальный ISBN-агент) | Открытого bulk-API в ходе анализа не обнаружено | Авторитетный источник по ISBN, зарегистрированным в РФ | Неизвестно/не обнаружено | ❌ Недостаточно данных, чтобы считать источником для MVP |
| **fantlab.ru и аналогичные фан-базы** | Официального публичного API нет | Сильное покрытие фантастики/фэнтези на русском силами сообщества | Только скрапинг | ❌ Скрапинг = нарушение ToS, исключено (см. Решение 1.d) |

**Итоговый выбор для MVP**: Wikidata (факты) + Open Library (обложки/обогащение), оба — по прямому API для точечных обращений и по официальным bulk-дампам для массовой выгрузки.

**Честное ограничение, которое нужно явно принять**: ни один из легально открытых источников не даёт глубокого покрытия современной русской жанровой/самиздат-литературы — это данные, которых в открытых структурированных базах просто нет в достаточном объёме. Реалистичный результат MVP-харвестинга — сильный каталог классики и широко известных произведений (в т. ч. хорошо покрытых на русском языке), а не витрина уровня ЛитРес/Озон по новинкам. Это ожидаемо и достаточно для наполнения каталога перед запуском; закрытие пробела по современной русской литературе — отдельная задача (партнёрство или ручное пополнение), см. Открытые вопросы.

### Решение 2. Как книги должны попадать в БД технически — сравнение способов наполнения

| Способ | Плюсы | Минусы | Когда уместен |
|---|---|---|---|
| **A. Расширить `cmd/seed`-подход**: отдельный CLI (условно `cmd/harvest`), который сам обращается к внешним источникам (Wikidata/Open Library) по заданному списку/запросу и пишет в БД напрямую через GORM (по образцу `FirstOrCreate` по `slug`) | Быстро реализуется, переиспользует существующий паттерн; не ограничен временем HTTP-запроса — можно спокойно выдерживать паузы между запросами к внешним API (rate limiting), что критично именно при работе с внешними источниками; не требует UI | В обход HTTP-слоя — нет аудита «кто и когда запустил импорт» через обычные admin-логи (это операция ops/разработчика, не контент-менеджера); требует доступа к серверу/БД | Первоначальное наполнение каталога из внешних источников перед публичным запуском; периодические «дозагрузки» новых произведений по каталогу источника |
| **B. Массовый импорт через admin API**: эндпоинт `POST /api/v1/admin/books/import`, принимающий **либо** файл (CSV/JSON, если когда-нибудь появится), **либо** список идентификаторов (ISBN/Wikidata QID) для запроса к внешнему источнику **синхронно внутри HTTP-запроса** | Доступен контент-менеджерам без доступа к серверу | При работе с внешними источниками синхронный HTTP-запрос ограничен их сетевой задержкой и rate limit — партия даже в 50-100 позиций рискует не уложиться в разумный таймаут запроса; фактически не годится как способ **массового** внешнего харвестинга | Только для файлового пути (если появится готовый файл) или для очень маленьких партий (единицы позиций) через внешний источник |
| **C. Полноценный ETL с очередью/воркером** (запуск задачи → асинхронная обработка → прогресс-бар → уведомление) | Снимает ограничение на время HTTP-запроса; лучший UX для очень больших внешних харвестов | Требует новой инфраструктуры (очередь/воркер), которой в проекте сейчас нет вообще — существенное расширение архитектуры backend | Оправдано, если объём регулярного харвестинга (Открытый вопрос OQ-001) станет настолько большим/частым, что CLI, запускаемый вручную, перестанет быть практичным |
| **D. Оставить только ручной ввод через существующую форму** (статус-кво) | Ничего не разрабатывать | Не масштабируется; не решает исходную проблему («нет данных») | Не рекомендуется как единственный способ |

**Рекомендация**: **A** — как основной канал массового харвестинга из внешних источников (не ограничен HTTP-таймаутом, естественно поддерживает rate limiting и паузы, требуемые этикетом Wikidata/Open Library). **B** — сохранить, но переопределить её роль: не «массовый импорт из внешних API», а (i) резервный путь для гипотетического будущего файла и (ii) единичный синхронный lookup-запрос для UX-ассистента в форме создания книги (см. Решение 4). **C** — отложить до подтверждённой необходимости регулярного крупнообъёмного харвестинга.

### Решение 3. Как обрабатывать авторов и жанры при импорте (в отличие от одиночного создания через форму)?

Одиночная форма в `admin/service` ожидает существующие ID автора/жанра. При массовом импорте источник данных обычно содержит **имена**, а не ID, и один и тот же автор может быть написан по-разному («Лев Толстой» / «Толстой Л. Н.» / «Leo Tolstoy»).

| Вариант | Оценка |
|---|---|
| a) Сопоставление по точному совпадению нормализованного (нижний регистр, без лишних пробелов) имени; при отсутствии — создание нового автора/жанра «на лету» | ✅ Рекомендуется для MVP. Простое, предсказуемое поведение; риск дублей смягчается тем, что импорт — контролируемая операция с построчным отчётом, где дубли автора видны сразу после импорта и исправимы через существующее редактирование |
| b) Нечёткое сопоставление (fuzzy matching) по схожести строк | ❌ Избыточно для MVP: усложняет реализацию и тестирование ради проблемы, которая при разумно подготовленном источнике данных (Решение 1) возникает редко; риск ложных склеек (два разных автора с похожими именами) хуже, чем риск дублей, который решается вручную |
| c) Обязательное ручное сопоставление каждого автора/жанра перед импортом (шаг предпросмотра) | ⚠️ Хорошая практика как часть UX предпросмотра (показать, какие авторы/жанры будут созданы заново, а какие сопоставлены с существующими), но не должна быть блокирующим требованием MVP — усложняет поставку первой версии | 

**Рекомендация**: (a) как базовое поведение + элемент предпросмотра из (c) в отчёте об импорте («будет создано N новых авторов: [...]») без обязательного интерактивного подтверждения на MVP.

### Решение 4. Где именно в продукте появляется обращение к внешним источникам

| Вариант | Оценка |
|---|---|
| a) Только офлайн-харвестер (способ A) — единственная точка интеграции с внешними API | ✅ Достаточно для решения исходной проблемы (пустой каталог) и ничего не добавляет в риск-поверхность admin HTTP API |
| b) + точечный синхронный lookup в форме создания книги в админке («Найти по ISBN/названию» → подставить поля из Open Library, администратор проверяет и сохраняет сам) | ✅ Рекомендуется добавить: дешёвая, низкорисковая (один внешний запрос на клик, тот же паттерн, для которого Open Library и предназначает свой live-API) фича, ощутимо ускоряющая ручное пополнение каталога уже после первичного харвеста |
| c) Импорт «в один клик» без предпросмотра (харвестер сразу публикует книги без возможности проверки) | ❌ Не рекомендуется для MVP: Wikidata — краудсорсинговый источник, возможны отдельные ошибки/вандализм в данных; нужен хотя бы минимальный отчёт для последующей выборочной проверки (созданные книги — черновики, см. FR-011/OQ-002) |

**Рекомендация**: (a) + (b). Точка c) (автопубликация без проверки) отклонена.

## Техническая реализация: что нужно сделать в проекте

Ниже — состав изменений, вытекающий из Решений 1–4. Это всё ещё продуктовый/архитектурный уровень детализации (для реализации нужен отдельный архитектурный документ), но описывает объём и затрагиваемые части кодовой базы достаточно, чтобы оценить работу.

1. **Новый internal-пакет клиентов внешних источников**, например `backend/internal/pkg/bookdata/`:
   - Общий интерфейс нормализованной записи (`ExternalBookRecord`: `Title`, `Authors []string`, `Genres []string`, `ISBN *string`, `Description *string`, `CoverURL *string`, `PublishedYear *int`, `PageCount *int`, `Language string`, `SourceName string`, `SourceID string`) — форма, совместимая с существующим `admin.BookInput`, чтобы дальше переиспользовать `CreateBook` без второй реализации валидации (см. NFR-001 выше).
   - `WikidataClient` — обращения к публичному SPARQL-эндпоинту (`query.wikidata.org`) с заранее подготовленными запросами (например: «литературные произведения с `ru`-подписью и автором из заданного списка/категории»); парсинг JSON-результатов SPARQL в `ExternalBookRecord`.
   - `OpenLibraryClient` — обёртка над Books API / Search API / Covers API для обогащения записи (описание, page count, обложка) по ISBN или названию+автору.
   - Оба клиента: обязательный описательный `User-Agent` с указанием проекта и контакта (этого явно просят и Wikimedia, и Open Library), таймауты, повторные попытки с экспоненциальной задержкой при 429/5xx, встроенный троттлинг запросов (не «тугой» цикл без пауз).
2. **CLI-харвестер** `backend/cmd/harvest` (по образцу `backend/cmd/seed`):
   - Вход: файл со списком целей для харвеста (названия/ISBN/Wikidata QID) **или** предустановленный SPARQL-запрос/категория.
   - Последовательно вызывает `WikidataClient` (источник фактов) → дополняет результат через `OpenLibraryClient` (обложка/описание, если Wikidata их не дала) → вызывает **тот же** сервисный метод создания книги, что использует admin API (`admin.Service.CreateBook`), — не отдельную копию правил валидации/slug/ISBN.
   - Идемпотентен по внешнему идентификатору (см. п. 4) — повторный запуск не плодит дубли.
   - На выходе — сводка по образцу `cmd/seed` (создано / пропущено / ошибка по каждой позиции).
3. **Расширение admin API одним новым эндпоинтом**: `GET /api/v1/admin/books/lookup?isbn=...` (или `?q=...`) — синхронный вызов `OpenLibraryClient` для одной позиции, `RoleAdmin`-защищён (переиспользует существующий `middleware.Auth` + `RequireRole`), результат используется только для предзаполнения формы создания книги на фронтенде — сохранение по-прежнему идёт через существующий `POST /api/v1/admin/books`.
4. **Миграция БД**: добавить в `books` (и, если понадобится, `authors`) нулевые (nullable) `external_source VARCHAR(50)` и `external_id VARCHAR(255)` + частичный уникальный индекс `(external_source, external_id) WHERE external_source IS NOT NULL`. Это меняет более раннее допущение «изменения схемы не требуются» (см. обновлённый NFR ниже) и нужно для идемпотентного повторного харвеста/будущей ресинхронизации с источником — без этого у CLI нет надёжного способа отличить «уже импортированную из Wikidata книгу» от «книги с таким же slug, случайно созданной вручную».
5. **Обработка обложек и лицензий**: `cover_url` заполняется автоматически только из Open Library Covers API (тот же паттерн, что уже используется в seed-данных, лицензионно пригоден для прямого хотлинка). Изображения из Wikimedia Commons (через `P18` в Wikidata), требующие обязательной атрибуции по CC-BY-SA, в MVP **не** импортируются автоматически в `cover_url` — в модели данных и UI сейчас нет места для отображения атрибуции обложки.
6. **Явно исключить Google Books** из любого пути, сохраняющего результат в БД, — его ToS прямо запрещает создание/хранение базы данных из ответов API.

## Бизнес-цель

1. **Готовность к запуску**: каталог из нескольких десятков демонстрационных книг классики недостаточен для публичного запуска книжного сервиса; наполнение каталога — блокер выхода на рынок, а не второстепенное улучшение.
2. **Операционная эффективность**: контент-команда должна иметь возможность добавлять книги пакетами, а не по одной через форму — иначе стоимость наполнения каталога линейно растёт с числом книг и не масштабируется.
3. **Фундамент для остальных фич**: поиск/фильтры, полки, рейтинги, списки, вызовы чтения — все зависят от объёма и качества каталога; их продуктовая ценность не может быть оценена на демо-данных.

## Проблема пользователя

Здесь «пользователь» — внутренний контент-оператор (администратор/контент-менеджер), а не читатель.

1. Единственный существующий способ добавить книгу — заполнить форму по одной книге за раз; для каталога в сотни/тысячи позиций это непрактично.
2. Нет способа загрузить уже существующий у продукта список книг (например, таблицу от партнёра/издательства) без ручного перепечатывания каждой строки в форму.
3. Нет способа проверить корректность данных пакета до применения — ошибка в одной строке файла не должна ни блокировать весь импорт, ни быть незамеченной.
4. Нет разделения между «загрузить сырые данные» и «доверенное содержимое каталога» — при импорте из недостаточно проверенного источника нужен способ придержать книги от публичного показа до ручной проверки.

## Целевые пользователи

| Сегмент | Роль в системе | Потребность |
|---|---|---|
| Контент-менеджер / администратор каталога | `RoleAdmin` (существующая роль) | Быстро добавить книгу через поиск по ISBN/названию вместо ручного заполнения всех полей; при появлении готового файла — загрузить его пакетом |
| Разработчик / ops | доступ к серверу/БД, вне HTTP-ролей | Запустить харвестинг каталога из внешних источников (Wikidata/Open Library) при первоначальном наполнении и периодических дозагрузках |

Роль `RoleModerator` в модерации импорта не участвует (роль администрирования каталога у неё и так отсутствует — см. `docs/features/admin.md`).

## Пользовательские сценарии

### SCN-001. Первоначальное наполнение каталога из внешних источников перед запуском (способ A)

- **Актёр**: разработчик/ops.
- **Предусловия**: подготовлен список целей харвестинга (SPARQL-запрос/категория Wikidata или список названий/ISBN).
- **Шаги**: запуск `cmd/harvest`; инструмент запрашивает Wikidata (факты) → дополняет через Open Library (обложка/описание) → валидирует и создаёт книги/авторов/жанры в БД тем же кодом, что и одиночное создание в админке, выводит сводку (создано/пропущено/ошибки).
- **Результат**: каталог наполнен; повторный запуск с тем же списком целей идемпотентен (существующие книги по `external_id` не дублируются).

### SCN-002. Плановое пополнение каталога контент-менеджером через поиск (способ B/Решение 4.b)

- **Актёр**: администратор.
- **Предусловия**: администратор открыл форму создания книги в админке.
- **Шаги**: администратор вводит ISBN или название в поле поиска и нажимает «Найти»; система запрашивает Open Library и предзаполняет поля формы (название, авторы, обложка, описание, год, объём); администратор проверяет, при необходимости правит значения и сохраняет книгу как обычно через `POST /books`.
- **Результат**: книга создана с данными, подтверждёнными человеком, без ручного набора всех полей с нуля.

### SCN-002a. Импорт из файла, если он появится (резервный путь способа B)

- **Актёр**: администратор.
- **Предусловия**: подготовлен файл с новой партией книг (десятки-сотни строк) — например, выгрузка от будущего партнёра.
- **Шаги**: администратор в админ-UI загружает файл на экран импорта; система валидирует построчно и показывает предпросмотр (сколько будет создано книг, новых авторов, новых жанров, сколько строк с ошибками/конфликтами); администратор подтверждает; система применяет валидные строки, невалидные остаются в отчёте с описанием причины.
- **Результат**: валидные книги добавлены в каталог (видимость — см. Решение по умолчанию видимости в FR-006); отчёт об импорте доступен для проверки.

### SCN-003. Строка с ошибкой в пакете

- **Актёр**: администратор.
- **Предусловия**: импортируемый файл содержит строку без обязательного поля (например, без названия) или с невалидным ISBN.
- **Результат**: эта строка помечена как ошибочная с указанием причины и не создаёт запись; остальные валидные строки пакета обрабатываются независимо (частичный успех — не «всё или ничего» на уровне файла).

### SCN-004. Повторный запуск харвестинга по тому же списку целей (идемпотентность)

- **Актёр**: ops-скрипт (`cmd/harvest`).
- **Предусловия**: часть или все цели харвестинга уже были импортированы ранее (совпадение по `external_source`+`external_id`, при файловом импорте — по `slug`/ISBN).
- **Результат**: позиции, соответствующие уже существующим книгам, помечаются как «пропущено (уже существует)», а не создают дубли и не завершаются ошибкой.

### SCN-005. Импорт создаёт нового автора «на лету»

- **Актёр**: администратор.
- **Предусловия**: строка файла ссылается на автора, которого нет в БД.
- **Результат**: автор создаётся автоматически (slug из имени, по аналогии с одиночным созданием); в отчёте об импорте автор отмечен как «создан новый» для последующей ручной проверки на дубли.

## Функциональные требования

- **FR-001**. Система предоставляет способ создать пакет книг за одну операцию, без необходимости отдельного HTTP/CLI-вызова на каждую книгу.
- **FR-002**. Формат входных данных — CSV или JSON, задокументированный (обязательные и опциональные поля соответствуют полям `Book`: `title`, `authors[]`, `genres[]`, `isbn`, `description`, `cover_url`, `published_year`, `page_count`, `language`; `slug`, если не указан, генерируется из `title` по существующему алгоритму `slugify`).
- **FR-003**. Валидация каждой строки переиспользует существующие правила из `admin/service` (обязательность/тримминг названия, URL-безопасность и уникальность `slug`, формат ISBN-10/13 после нормализации, положительные разумные `published_year`/`page_count`) — правила не дублируются отдельной реализацией.
- **FR-004**. Обработка построчная и независимая: ошибка в одной строке не отменяет обработку остальных строк того же пакета (частичный успех, не транзакция на весь файл).
- **FR-005**. Авторы и жанры, указанные по имени и отсутствующие в БД, создаются автоматически по правилам, аналогичным одиночному созданию (Решение 3.a); существующие сопоставляются по нормализованному имени.
- **FR-006**. Книги, созданные путём импорта, по умолчанию видимы в публичном каталоге, если импортирующий явно не указал признак черновика (`is_hidden = true`) для данного пакета — окончательное решение о значении по умолчанию см. OQ-002.
- **FR-007** (способ B). По завершении обработки пакета система возвращает отчёт: число обработанных/созданных/пропущенных (уже существует)/ошибочных строк и, для каждой ошибочной строки, номер строки и причина.
- **FR-008** (способ B). Массовый импорт доступен только пользователю с ролью `RoleAdmin`, через тот же механизм авторизации, что и остальные admin-эндпоинты (`middleware.Auth` + `RequireRole`).
- **FR-009** (способ A). CLI-инструмент для разовой загрузки — идемпотентен относительно повторного запуска с тем же файлом (сопоставление по `slug`, аналогично `cmd/seed`).
- **FR-010**. Массовый харвестинг из внешних источников (Wikidata + Open Library) выполняется офлайн-CLI-инструментом (способ A), а не синхронным admin HTTP-эндпоинтом — обращения к внешним API не должны быть ограничены временем HTTP-запроса и обязаны соблюдать паузы между запросами.
- **FR-011**. Каждая книга (и, где применимо, автор), созданная харвестингом из внешнего источника, сохраняет идентификатор источника (`external_source`, `external_id`), обеспечивая идемпотентность повторного запуска и возможность будущей ресинхронизации.
- **FR-012**. Форма создания книги в админке получает необязательное действие «Найти по ISBN/названию», выполняющее синхронный запрос к Open Library и предзаполняющее поля формы; сохранение книги остаётся явным действием администратора через существующий `POST /books`.
- **FR-013**. Обложка (`cover_url`) автоматически заполняется только из источников, не требующих обязательного отображения атрибуции (Open Library); изображения, требующие атрибуции (Wikimedia Commons), в MVP не импортируются автоматически.

## Нефункциональные требования

- **NFR-001**. Импорт не должен вводить вторую независимую реализацию бизнес-правил валидации книги — переиспользуется код `admin/service` (прямой вызов существующих функций/сервисных методов, а не копирование логики).
- **NFR-002**. Размер файла для синхронного HTTP-импорта (способ B) ограничен разумным пределом (порядок — сотни строк), задокументированным как явное ограничение MVP; не блокирует UI на неопределённое время. Файлы большего объёма — через способ A (CLI). **Решено** (см. `docs/features/catalog-manual-import.md`): тело запроса ограничено 2 МиБ (413 при превышении, до разбора файла), число строк — 500 (422 при превышении, до обработки строк, с указанием использовать `cmd/harvest`/`cmd/seed`).
- **NFR-003**. Импорт не выполняет сетевые вызовы к внешним API в самом пути записи в БД (обогащение из внешних источников, если потребуется, — отдельный подготовительный шаг до импорта, не часть транзакции создания книги).
- **NFR-004** (обновлено). Требуется одна новая миграция: nullable `external_source`/`external_id` в `books` (см. «Техническая реализация», п. 4) — единственное изменение схемы, необходимое для этой фичи в её текущем, ориентированном на внешние источники, виде.
- **NFR-005**. Соответствие паттернам проекта: код способа B и эндпоинта lookup живёт в существующем модуле `backend/internal/modules/admin` (repository/service/transport), способ A и клиенты внешних источников — в `backend/cmd/` и `backend/internal/pkg/bookdata/` соответственно.
- **NFR-006**. Все исходящие запросы к внешним источникам данных передают описательный `User-Agent` с указанием проекта и контакта — согласно этикету Wikidata и Open Library.
- **NFR-007**. Массовый харвестинг троттлит запросы и реализует повтор с экспоненциальной задержкой при 429/5xx; не может выполняться как неограниченный по частоте цикл запросов к стороннему API.
- **NFR-008**. Контент, полученный через Google Books API, не сохраняется в БД ни при каких обстоятельствах — это прямо запрещено его ToS (запрет на создание/хранение базы данных из ответов API и на распространение контента без отдельного разрешения). Google Books не входит в рекомендованный набор источников MVP.

## Требования к валидации

- Обязательные поля строки: `title`, минимум один автор.
- `isbn`, если указан: валиден по ISO 2108 (ISBN-10/13) после нормализации — переиспользуется `isValidISBN` из `admin/service`; ISBN не проверяется на уникальность (в схеме БД её нет), но дублирующийся ISBN у разных `slug` не является ошибкой валидации (открытый вопрос по бизнес-желательности — см. OQ-003).
- `slug` (если указан явно, а не сгенерирован): URL-безопасен, уникален в рамках всего каталога (конфликт — строка помечается как ошибка/пропуск, не перезаписывает существующую книгу).
- `published_year`/`page_count`, если указаны: положительные целые числа в разумных границах (переиспользуются текущие правила одиночного создания).
- `language`: непустой поддерживаемый код (как в одиночном создании).
- Файл в целом: корректный CSV/JSON по заранее заданной схеме; полностью нечитаемый файл (не парсится) — общая ошибка импорта, не построчная.

## Сценарии ошибок

| # | Сценарий | Ожидаемое поведение |
|---|---|---|
| E-01 | Файл не парсится (битый CSV/JSON) | Импорт не запускается; понятная общая ошибка формата |
| E-02 | Строка без обязательного поля | Строка помечена ошибочной с причиной; остальные строки обрабатываются |
| E-03 | Невалидный ISBN в строке | Строка помечена ошибочной (если ISBN обязателен по политике) или ISBN игнорируется с предупреждением (если необязателен) — решение см. FR-003/валидация |
| E-04 | Дублирующийся `slug` (совпадает с уже существующей книгой) | Строка помечена «пропущено: уже существует», книга не изменяется (импорт не является операцией обновления) |
| E-05 | Импорт без роли `admin` (способ B) | 403, пакет не обрабатывается |
| E-06 | Обрыв соединения/таймаут на большом файле (способ B) | Явный предел размера (NFR-002) должен предотвращать сценарий; при превышении — отказ до начала обработки с указанием использовать способ A |

## Граничные случаи

- Пустой файл (только заголовки) — 0 обработанных строк, не ошибка.
- Одна и та же книга дважды в одном файле — первое вхождение создаёт книгу, второе обрабатывается как E-04 (уже существует после первого вхождения того же пакета).
- Автор указан с разным написанием в разных строках одного файла («Л. Толстой» и «Лев Толстой») — по правилу Решения 3.a будут созданы два разных автора; это ожидаемое поведение MVP, исправляется вручную через существующее редактирование авторов.
- Книга без обложки/описания — поля опциональны, книга создаётся без них (как и при ручном создании через форму).

## Границы MVP

### In scope

- Клиенты Wikidata и Open Library (`backend/internal/pkg/bookdata`) с нормализацией в общий формат записи книги.
- Способ A: CLI-харвестер (`cmd/harvest`), обращающийся к Wikidata/Open Library по заданному списку целей/запросу, идемпотентный по `(external_source, external_id)`.
- Способ B (переопределённая роль): эндпоинт единичного lookup (`GET /admin/books/lookup`) для ассистента в форме создания книги + сохранённая возможность файлового массового импорта на случай появления готового файла.
- Автосоздание отсутствующих авторов/жанров по точному совпадению нормализованного имени.
- Миграция БД: `external_source`/`external_id` в `books`.

### Out of scope (не входит в MVP)

- Обновление существующих книг через повторный харвест (харвестинг — только создание; редактирование остаётся через одиночную форму или отдельную фичу «массовое обновление/ресинхронизация»).
- Любое использование Google Books API для данных, сохраняемых в БД (см. NFR-008) — прямо запрещено его ToS.
- Интеграция с ЛитРес и Z39.50-доступ к каталогам РГБ/РНБ — вне MVP: первое требует партнёрского договора, второе — отдельного технического спайка (см. раздел «Источники данных»).
- Автоматический импорт обложек из Wikimedia Commons с обязательной атрибуцией (CC-BY-SA) — в модели данных сейчас нет места для отображения атрибуции.
- Асинхронная обработка/очередь/прогресс-бар для очень больших харвестов (способ C).
- Автоматическая загрузка изображений обложек в собственное хранилище (обложки остаются внешними URL, как сейчас).
- Нечёткое сопоставление (fuzzy matching) авторов/жанров.
- Интерактивный шаг подтверждения предпросмотра с возможностью построчного редактирования перед применением (может быть добавлен позже поверх отчёта харвестинга).
- Веб-скрапинг сторонних сайтов как источник данных.
- Закрытие пробела в покрытии современной русской жанровой/самиздат-литературы (открытые источники его не решают — см. «Источники данных: сравнительный анализ»).

## Открытые вопросы и риски

### Открытые вопросы

- **OQ-001** ~~Какой источник данных фактически будет использоваться?~~ **Решено**: Wikidata + Open Library (см. «Источники данных: сравнительный анализ»).
- **OQ-005 (новый, заменяет фокус OQ-001). Каким списком/запросом ограничить первый харвест?** Wikidata не умеет отвечать на вопрос «дай все хорошие книги» — нужен конкретный критерий отбора: например, «произведения с `ru`-подписью и ссылкой на статью в ru.wikipedia», «библиография по заданному списку авторов», «лауреаты конкретных литературных премий». Без этого критерия объём и состав первого харвеста не определён. **Статус: решено** (см. `docs/features/harvest-review-queue.md`) — способ A: курируемый список Wikidata author QID (`cmd/harvest -authors`/`-authors-file`) + фильтр по классу литературного произведения + ограниченный `LIMIT`, а не открытый категорийный запрос.
- **OQ-002. Видимость (`is_hidden`) книг сразу после харвестинга по умолчанию.** Рекомендация — учитывая, что Wikidata краудсорсинговая и в данных возможны единичные ошибки, создавать харвестингом книги с `is_hidden = true` (черновик) и публиковать пакетом после выборочной проверки по сводке `cmd/harvest`, а не сразу видимыми. **Статус: не блокирует, требует продуктового решения перед первым запуском харвестера.**
- **OQ-003. Нужна ли уникальность ISBN на уровне бизнес-правил (не только БД)?** При харвестинге из Wikidata у многих классических произведений ISBN отсутствует (ISBN как стандарт появился в 1970 году) — это ожидаемо, не ошибка. **Статус: не блокирует MVP; отсутствие ISBN у книги, созданной харвестингом, — нормальный случай, не требует специальной обработки сверх текущих правил (поле опционально).**
- **OQ-004. Формат входного списка целей для харвестера — файл с названиями/ISBN, файл с Wikidata QID или встроенный SPARQL-пресет (категория)?** Влияет на UX подготовки первого запуска. **Статус: архитектурное решение, не блокирует бизнес-анализ.**
- **OQ-006 (новый). Принимает ли продукт ограниченное покрытие современной русской литературы на старте?** Открытые источники дают сильный результат для классики и слабый — для новинок/жанровой прозы (см. «Источники данных»). **Рекомендация**: да, для MVP это приемлемо как способ быстро выйти из состояния «пустой каталог»; закрытие пробела — отдельная задача, не блокирующая эту фичу. **Статус: не блокирует, но должен быть осознанно принят продуктовой стороной, чтобы не оказаться сюрпризом после первого харвеста.**

### Риски

- **R-001 (средний)**. Отсутствие уникальности ISBN в схеме означает, что дедупликация полагается на `slug` (генерируется из названия) и новый `external_id` — два разных издания одной и той же книги в разных источниках могут теоретически создать дубль записи. Смягчение: `external_source`/`external_id` для дедупликации внутри одного источника; ручная проверка отчёта харвестера перед публикацией (OQ-002) как страховка от кросс-источниковых дублей.
- **R-002 (средний)**. Автосоздание авторов «на лету» по точному совпадению имени может размножить дубли авторов, если один автор встречается в данных под разными написаниями (см. Граничные случаи). Смягчение: предпросмотр в сводке харвестера («будет создано N новых авторов») + существующий UI редактирования авторов для последующей ручной консолидации.
- **R-003 (пересмотрен, низкий)**. Лицензионный риск по выбранным источникам закрыт анализом (Wikidata — CC0, Open Library — документированно открыта для такого использования); остаточный риск — точечная неточность формулировок лицензии могла устареть с момента анализа. Смягчение: при промышленной эксплуатации перепроверить актуальные условия использования перед первым продакшен-запуском харвестера.
- **R-004 (низкий)**. Способ A (CLI с прямой записью в БД) обходит уровень авторизации и аудита admin-API — приемлемо для контролируемой ops-операции, но не должен становиться единственным способом пополнения каталога навсегда (иначе теряется аудит «кто добавил книгу»). Смягчение: способ A — для харвестинга из внешних источников и первоначальной загрузки; повседневное ручное пополнение — через lookup-ассистент в админке (Решение 4.b), у которого аудит есть.
- **R-005 (средний, новый)**. Wikidata — краудсорсинговый источник: отдельные объекты могут содержать неточные факты (ошибочный автор, дата, жанр) или быть вандализированы. Смягчение: OQ-002 (черновик + ручная проверка перед публикацией), отчёт харвестера как основной инструмент выборочного контроля качества.
- **R-006 (низкий, новый)**. И Wikidata SPARQL-эндпоинт, и Open Library API — бесплатные публичные сервисы без гарантированного SLA; временная недоступность или снижение лимитов вне контроля проекта. Смягчение: харвестер — офлайн-инструмент, а не часть пользовательского пути; повторный запуск идемпотентен и безопасен при сбое на середине.

## Зависимости

**Готово (не блокирует):**

- Модель данных `Book`/`Author`/`Genre` и их связи (миграция `000001`).
- Admin-модуль с готовой валидацией (`slugify`, `isValidISBN`, транзакционное создание/связывание) — переиспользуется, не создаётся заново.
- Auth/`RequireRole` — переиспользуется для защиты эндпоинта импорта.
- Паттерн `cmd/seed` как основа для CLI-инструмента способа A.

**Внешние зависимости:**

- Доступность и стабильность публичных сервисов Wikidata SPARQL-эндпоинта и Open Library API/дампов — вне контроля проекта (см. R-006).
- Критерий отбора для первого харвеста (OQ-005) — организационно-продуктовая зависимость, определяющая объём первого запуска.

## Что не входит в фичу

См. «Границы MVP → Out of scope». Дополнительно явно исключено:

1. Любые изменения ценообразования/коммерческих данных (проект — каталог/сообщество, не магазин с ценами в текущей модели данных).
2. Модерация контента, добавленного харвестингом, сверх существующего механизма `is_hidden` (используется как есть для черновик/публикация, см. OQ-002).
3. Изменения схемы БД сверх одной миграции `external_source`/`external_id` (см. NFR-004).
